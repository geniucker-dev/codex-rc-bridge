# 真实手机验收

适用范围：从源码工作区启动独立的原生验收实例，使用官方移动客户端 A 和两台真实被控电脑 B/C。2026-11-08 按用户确认，iPad/iOS 的 B 基线及 B → C → B 基本切换记为已验证，切换后在 App 内刷新即可。实机操作在 iPad 完成，iOS 按用户确认的相同客户端逻辑纳入验收，不另行要求 iPhone 重复测试。IN 单个控制端撤权、重新配对及 IN/OUT 删除后的同名恢复已有用户确认和本机身份核对；B 离线恢复已由用户确认基本正常，有少量延迟；审批边界仍按下表验收。容器部署已另行验证，不要求再在容器里重复授权真实账号。

本轮沿革：先接入 B，随后已接入 C 并由用户在 iPad 完成来回切换。按用户要求，已将原固定链路的账号、租户种子、设备身份、密钥、注册、配对和绑定迁入管理实例，保留网页管理密码及会话，由管理实例接管运行。旧进程已停止，旧数据库已改名归档，不能再并行运行这份身份的副本。B 基线与后续切换可以复用迁入的 IN/OUT，免去重复登录与配对；下文 `accept-phone` / `accept-b` 在这两项中分别指代原 IN/OUT。

删除、撤权及同名恢复仍只使用下表中新建的独立测试端点，不能删除迁入的日常端点；这部分测试需要另行注册和配对。独立 OUT 可以指向同一个 B，但仍共享 B 的实际工作环境；测试对话使用无副作用的内容。关闭 B 的远控会影响所有连接 B 的控制端，离线测试只在用户安排的空闲时间执行。

## 启动验收管理页

在项目目录的真实终端运行：

```sh
bun run acceptance
```

脚本构建 release 程序，首次为用户名 `acceptance` 提示输入两次管理密码（至少 12 字符，输入不回显）。这是本地管理密码，不是 ChatGPT 密码。不要把密码、回调地址或配对码发到聊天或保存进验收记录。

前后端就绪后，终端才会显示 `http://127.0.0.1:15173`。在运行桥接的这台电脑上打开它；手机使用官方 ChatGPT/Codex 远程控制入口，通过云端连接 IN，不访问手机自身的 localhost。终端需保持运行；Ctrl+C 只停止此验收实例，等待后台工作完成并保留状态。再次运行同一命令可继续验收，不能重新初始化或换主密钥。

| 项目 | 独立位置 |
| --- | --- |
| 数据库 | `local-state/acceptance-v1/bridge.sqlite` |
| 主密钥 | `secrets/acceptance-v1/master.key` |
| 后端监听 | `127.0.0.1:18787` |
| 管理网页 | `127.0.0.1:15173` |
| 原日常状态 | 启动器不会自动导入；本轮已做一次离线迁移，原数据库改名归档，运行状态以验收目录为准 |

两个验收目录为 0700，密钥为 0600，均位于现有忽略目录中。数据库与密钥缺一时拒绝重新初始化；端口被占用时拒绝启动，不结束占用端口的进程。`bun run acceptance --prepare` 只准备状态，不创建管理密码、不启动网页或远控。

需要上游代理时，在首次 setup 提示中填写，或登录网页后进入“设置 → 上游代理”。已有单用户管理账号升级后具有部署管理员权限。配置加密持久化，并通过“保存并应用”直接生效，无需重启或反复设置环境变量。旧环境代理仅在首次没有保存配置时导入。

端口以本机代理实际配置为准；此处是原生进程，不使用容器的 host.docker.internal。代理覆盖授权和控制两个域名，不自动照搬 OrbStack 的 SOCKS 配置；管理网页仍仅监听回环地址。

## 先建立 B，再添加 C

全新初始化的实例不继承日常桥接身份；本轮已完成离线迁移，可跳过下面已有账号及 B 链路的创建步骤，直接刷新网页、确认迁入连接并从手机验证 B。C 准备好后再添加它的账号和 OUT。B/C 的官方客户端不需要退出或更换现有账号。

迁移保留原租户与加密主密钥，完整复制加密状态，并把现有管理用户关联至迁入租户；不能仅复制令牌而重新生成设备身份。迁移前两边均须正常停止并持有数据库锁，保留原状态及目标管理库/密钥的私有备份，验证外键、完整性、身份与密文一致后才启动接管。旧库归档仅用于恢复，不会随新库续期更新；不能当作可并行运行的第二实例。备份位置只记录在忽略目录中的 `import-receipt.json`。

| 固定名称 | 所属账号 | 用途 |
| --- | --- | --- |
| `accept-phone`（IN） | 手机 A 的账号 | 整个切换验收使用同一个入口 |
| `accept-b`（OUT） | B 所在账号 | 配对并固定选择 B |
| `accept-c`（OUT） | C 所在账号 | 配对并固定选择 C，稍后添加 |

1. 在“账号”添加 A 与 B 所属账号。相同账号只登录一次；回调直接提交到管理网页。
2. 在“出口 OUT”添加 `accept-b`，完成该出口的单独授权、配对 B，并选择 B 为目标。不能直接拿已被日常 IN 占用的 OUT 做测试。
3. 在“入口 IN”添加 `accept-phone`，绑定 `accept-b`，生成配对码并在手机 A 完成配对。启动此测试链路，确认网页显示“连接可用”。
4. 手机进入 `accept-phone`，打开专用测试对话，确认列表与回复来自 B。到这里先停留，不必立即添加 C 或做删除。
5. C 准备好后，添加它所属的账号（若已存在则复用），新建并授权 `accept-c`，配对、选择 C。暂时不要绑定另一个 IN，保证它可用于切换。

同一 OUT 不能同时绑定两个 IN。不同 OUT 可以选择同一真实电脑，但完整 B/C 验收必须选择两个不同的目标环境；两个名字都指向 B 不算切换验收。

## 删除测试专用端点

基本切换已完成；以下删除与恢复步骤另建 `revoke-test-in` 和 `revoke-test-out`。它们不是迁入日常端点的别名，不能用日常 IN 或现有 OUT 代替。复用已登录的 A/B 账号，测试 OUT 单独完成授权与配对 B，再创建测试 IN 并绑定测试 OUT，由 iPad 配对测试 IN。测试开始前在本机记录设备 ID 的哈希；原日常绑定与启用状态保持不变。

2026-11-08 准备进度：独立测试 OUT 已完成授权、配对并选择 B；测试 IN 已创建、绑定并启动，两侧连接已建立，已生成手机配对码，用户已确认测试入口正常。随后按用户要求补齐 IN 的允许连接及控制端管理，单个控制端撤权已按用户反馈通过，并核对本地 IN 身份、注册、绑定和日常配置保留；用户随后确认生成新码重新配对后恢复正常，设备 ID 与原基线一致；用户随后删除测试 IN；移除配对窗口等待逻辑并升级到 schema 8 后，后端已完成该 IN 的撤权清理，待删除端点归零，日常端点、绑定与启停配置哈希一致，原链路重新连接。用户随后完成测试 IN 同名重建和配对，本机核对 IN 设备 ID/派生上下文一致，OUT 设备 ID、注册公钥指纹及注册 ID 保持不变。用户随后完成测试 OUT 删除、同名重建、授权配对与重新绑定，并确认正常使用。本机核对 IN/OUT 设备 ID 与派生上下文保持一致，OUT 注册公钥指纹保持一致，上游 client ID 已变化；测试绑定恢复且启用，待删除端点为零，日常端点、绑定和启停状态与基线哈希一致。IN/OUT 删除后同名恢复的基本流程已通过。已在本机保存测试设备 ID、OUT 注册公钥标识与日常配置的哈希基线，并确认准备过程中日常端点、绑定和启用状态不变。8 项生命周期回归及 1 项删除协调回归通过，覆盖按环境撤权、失败保留、同名身份恢复、旧回调拒绝及另一链路保持运行；这些使用合成服务，不计为真实撤权通过。

## 验收顺序与通过标准

| 顺序 | 操作 | 通过标准 |
| --- | --- | --- |
| 1. B 基线 | 在 B 准备可辨认的测试对话，手机从测试 IN 打开并发送一条无工具调用的消息 | 列表、回复和所在目标一致；日常入口仍能使用 |
| 2. B → C | 管理页对 `accept-phone` 点“切换出口”，选择 `accept-c` | 旧链路结束，新连接指向 C；必要时手机退出设备页再进入，之后列表/消息必须来自 C |
| 3. C → B | 同样切回 `accept-b` | 能重新初始化 B；C 的消息不能进入 B，不自动重发上次切换前的命令 |
| 4. 审批边界 | 若现有安全策略能自然触发一条无副作用的待审批操作，在它等待时切换目标 | C 不出现 B 的审批，不把旧审批或命令送给 C；B 已开始的任务允许继续执行，切换不等于取消 B 的任务 |
| 5. B 离线恢复 | 在空闲时间手动关闭 B 的远控，再恢复 | 网页和手机体现离线；绑定仍保留；恢复后自动连接，必要时重新进入设备页；若有独立指向 C 的链路，它不应停止 |
| 6. 删除测试 IN | 仅删除 `revoke-test-in`，保留 OUT 和日常 IN | 测试链路停用、解绑；原手机不能继续通过旧测试环境控制 B/C；日常 IN 的配对权限仍有效 |
| 7. 恢复同名 IN | 删除明确完成后，以相同账号/固定名称创建 `revoke-test-in` | 本地设备 ID 相同；完成注册、配对后可使用 |
| 8. 删除测试 OUT | 将测试 IN 绑定到 `revoke-test-out`，再仅删除 `revoke-test-out` | 关联测试链路停用、解绑；仅撤销测试 OUT 的注册，B 的远控及日常 OUT 仍可使用；保留 IN 和共享账号 |
| 9. 恢复同名 OUT | 删除明确完成后，以原账号/固定名称新建 `revoke-test-out`，重新授权、配对 B、保存目标并绑定 | 本地设备 ID 保持；原密钥规则保持；重新授权后可用，上游新注册编号允许不同 |

固定 IN 名称保持不变是预期行为，不能要求每次切换都把 IN 改名或重新注册。目标的对话、消息和审批归属必须正确；版本/展示元数据若仍旧，单独记录其是否影响使用，不通过修改注册协议来掩盖问题。

手机允许在硬切换后手动退出设备页面并重新进入。如果重新进入后仍显示旧对话、持续超时或审批错投，则该项失败；不要为了“通过”删除重建测试 IN。没有可用审批场景时记“未覆盖”，不要放宽实际设备的安全设置。

## 删除与恢复的观察边界

- “已停用”或“撤权待完成”都不等于删除完成。撤权失败时修复账号授权或网络后重试清理，确认端点删除成功。
- 未确认远端撤权时不重建同名身份，也不删除数据库来绕过。缺失历史注册信息时按 [修复限制](AUTHORIZATION.md#缺失-out-注册记录的修复) 保留待处理。
- 删除前在本机确认测试端点的“设备身份”和固定名称；删除仅限本轮新建的 `revoke-test-in` / `revoke-test-out`，不能仅凭名称前缀判断。不要停止或删除日常桥接的注册。
- 网页可以核对本地设备 ID；公钥稳定性已有固定向量与核心回归。若本轮未独立观察到公钥，不把“ID 相同”写成“真实注册公钥已独立验证”。
- 官方界面若无法区分测试与日常注册，不以设备列表数量推断撤权范围。记录实际可观察的旧入口失效、日常入口继续可用、重新授权后恢复等结果，并保留不可观察项。
