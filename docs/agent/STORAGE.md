# SQLite 测量与恢复

存储选型和变更条件集中在 [计划](PLAN.md#存储选择与边界)。本文记录可复现的验证、测量限制与离线恢复步骤，不将本机结果换算为服务器用户容量。

## 可重复验证

```sh
# 常规回归包含强杀事务回滚、离线数据库恢复、服务器与独立密钥文件恢复。
cargo test --workspace --locked

# 显式运行磁盘负载测量；默认回归跳过它，避免把机器性能作为 CI 通过条件。
cargo test -p bridge-core --locked --release --lib storage::capacity::sqlite_capacity -- --exact --ignored --nocapture
```

两项命令均使用自己的临时目录和合成数据；服务器测试仅监听回环地址，链路停用，不访问上游。退出后清理测试数据与子进程，不读取现有部署。测量输出只有环境、配置、记录数、耗时和文件大小。

Linux 容器测量使用独立镜像目标，不把测试程序加入生产镜像。构建时先运行 Rust 回归，运行时使用与服务器相同的 UID 和持久卷挂载位置：

```sh
docker build --target storage-measure -t codex-rc-bridge-storage-measure:local .
docker run --rm --network none --read-only \
  --mount type=volume,target=/var/lib/bridge \
  codex-rc-bridge-storage-measure:local
```

这里未指定卷名，会创建独立匿名卷，并在 `--rm` 容器退出时删除，见 [Docker 卷生命周期](https://docs.docker.com/engine/storage/volumes/#named-and-anonymous-volumes)；不得改为现有部署的数据库卷。`TMPDIR=/var/lib/bridge` 确保测量数据库位于卷内，不使用 `/tmp` 的内存文件系统。JSON 中 `fullfsync: true` 表示请求该 SQLite 选项，Linux 并没有 macOS 的额外刷盘语义。

容器卷恢复由 `bun run test:container` 验证，需先按 [容器部署测试说明](AUTHORIZATION.md#docker-compose-部署) 构建服务器和网页镜像。测试停服后将数据库卷和密钥卷分别归档到两个私有测试卷，移除源卷，在空卷中恢复，再检查文件哈希、密钥属主/权限及原管理会话。归档助手需要保留 UID/GID，因此仅这个离线助手以 root 运行，禁网且只挂载测试卷；服务仍使用 UID 10001、只读根文件系统和只读密钥挂载。测试结束清理自己的容器、网络、数据卷与归档卷。

## 负载与测量边界

[测量代码](../../crates/bridge-core/src/storage/capacity.rs) 使用当前存储接口和持久化策略：单连接、`DELETE`、`EXTRA`、外键及 `fullfsync`。每组创建独立磁盘库，预填 0 或 100,000 条防重放记录；启动 1、8 或 32 个并发任务，每个任务对应独立租户，连续发起 200 次操作：

- 60% 调用 `claim_stream`，登记新的源流。
- 30% 读取并解密 1 KiB 合成凭据记录。
- 10% 加密并写入 1 KiB 合成凭据记录，模拟续期的存储部分，不含上游请求。

每个任务同时只有一个未完成请求，不设请求间隔；任务的操作序列错开。报告包括整个接口调用的排队、SQL 和加解密耗时。预填历史、建表及初始凭据写入不计入负载耗时；预填后直接运行，因此并非冷缓存测试。

另起一轮相同并发量的显式事务探针，每个任务执行 64 次单行插入，分别记录获取连接的等待和 `COMMIT` 耗时。它与生产接口的自动提交实现不同，不能把探针数字当成同一批 `claim_stream` 调用的内部耗时分解。每组结束核对全部新增记录数，任何操作错误使测量失败。

这是一轮有限样本、持续提交的合成压力基线，不是最大吞吐、长期稳定性或真实聊天延迟验收；单任务下凭据写入只有 20 个样本，p99 等高分位尤其不能视为稳定上限。没有测量 WebSocket、上游延迟、管理页面完整快照或账号密码哈希的成本。换机器、磁盘、容器卷或日志策略后需要在目标环境重新测量；生产负载也可能不同于这里的写入比例。

## 2026-11-08 本机结果

环境：macOS 27.0.1（26A434）、arm64、Rust/Cargo 1.99.1、SQLite 3.46.0、release 构建；数据库位于本机 Data 卷上的临时目录。测量时没有并行运行本项目构建或测试，宿主原有应用继续运行；未控制系统后台 I/O。共完成 16,400 次混合接口操作和 5,248 次事务探针，无错误；[原始分位数与文件大小](validation/sqlite-macos-arm64-2026-11-08.json) 可用于后续比较。

这轮测量确认单连接在持续并发写入下会让读请求一同排队：32 个任务时，新流与凭据读取 p95 均约 0.25 秒，观测到的新流最慢调用约 0.79 秒。因此不能宣称并发量与延迟无关。100,000 条历史下单任务与 8 任务组也出现更慢提交或长尾；各组的磁盘布局、缓存和宿主负载未完全控制，不能仅凭这轮结果归因于历史条数，也不能反推增加任务会改善单次请求性能。

32 个持续提交任务下，新流 p95 约 0.10–0.15 秒，但整轮最慢一次新流登记约 1.33 秒。平均吞吐改善不代表长尾消失。这是同一台 macOS 宿主上的 Linux 虚拟机卷测量，不能作为物理 Linux 主机、云盘或所有容器部署的容量承诺，也不能据此认为 Linux 的断电持久性优于 macOS；两种环境的刷盘路径不同。

目前保留 SQLite 和现有持久化策略。目标服务器若在实际新流/续期速率下出现不可接受的等待，应先定位并测量事务合并、查询与连接安排的改进，同时保留“提交成功才允许转发”的语义；仍不满足要求时按计划评估 PostgreSQL。现有两组样本不构成数据库迁移依据，也不构成无限容量承诺。

## 离线恢复演练

[核心测试](../../crates/bridge-core/src/storage/tests.rs) 验证已提交数据与未提交事务的强杀恢复，以及备份中的绑定、目标、启停状态、待删除状态、加密注册检查点、租户隔离和旧流拒绝。进程强杀不模拟断电或硬盘故障。

[服务器测试](../../crates/bridge-server/tests/server.rs) 使用真正的主密钥文件与服务器可执行文件：

1. 创建合成租户、管理用户、IN/OUT、停用的绑定、设备密钥派生材料、防重放记录与未完成 OAuth 事务，启动服务器并登录。
2. 正常 SIGTERM 退出，确认进程结束及数据库锁释放；把数据库与原密钥分别复制到新的私有目录，删除测试源目录。
3. 从新位置打开数据库，核对设备 ID、公钥、绑定及旧流拒绝；以匹配的拒绝授权回调解密并消费恢复的 OAuth 事务，验证只能消费一次，全程不交换令牌。
4. 验证缺失或错误的主密钥会拒绝启动，不自动生成替代密钥；随后用原密钥启动，原管理账号和原会话均可读取相同设备及停用绑定，再正常退出。

上述 Rust 恢复测试已在 macOS 和 OrbStack Linux arm64 通过。另有 1 项 Playwright Compose 测试在当前 release 镜像上通过：停服后分别归档数据库与密钥卷，删除源卷，在空卷恢复，核对两份文件的哈希及密钥 UID/GID/0600 权限；启动后原管理会话仍可访问，并继续通过 HTTP/本地 HTTPS 登录退出、Host/Origin/CSRF、只读挂载、权限错误拒绝启动及 SIGTERM 检查。测试容器、网络、数据卷、归档卷和浏览器均已结束或清理。

这覆盖同机容器卷的离线归档恢复，尚不覆盖异机灾备、正式备份服务或目标云盘。它不表示旧备份中的官方令牌、注册或配对在上游仍有效，也不测试已启用链路恢复后的远控。无需为这些部署测试再次授权真实账号。

## 账号登录状态

当前 schema 的 `accounts.sign_in_required` 是持久布尔值，按租户、工作区和用户隔离。存量凭据缺失、缺少 refresh token、所属身份不匹配或刷新返回身份不符，以及 OAuth 明确返回 `invalid_grant`、`refresh_token_expired`、`refresh_token_reused` 或 `refresh_token_invalidated` 时设为 true，并递增内部 `sign_in_revision`。当次登录回调的身份校验失败不改变存量标记。无 OAuth 字符串错误、且 code 不是已知凭据失效码的 4xx，以及 408、429、5xx 和网络失败保留原值并重试；其他明确的 OAuth 错误保留标记原值并停止自动重试，连接报告带来源一端的 `failed`，由用户手动重试。账号登录成功后清除。检查已标记账号必须实际续期，检查通过仅能清除开始时修订号仍匹配的标记，不能覆盖并发的新失败。读取快照不发起续期，也不清除标记。设备二次授权和 OUT 注册失败不设置账号标记。

数据库结构统一放在 `crates/bridge-core/src/schema.sql`，使用版本 14，仅初始化空库、接受当前版本；其他版本及非空无版本库在打开时拒绝并明确提示数据库结构不受支持、需要手工处理。同结构库的备份与恢复保留账号标记、身份、未完成操作和链路启用设置。

## 结构变更与迁移

已发布版本的部署要能直接升级，所以迁移按发布版计算，不按开发中的每次改动计算。每个发布版只需支持从上一个发布版的数据库版本升级到自己的版本：两次发布之间结构改了几次，都合并成一个从上一发布版到当前结构的迁移，不为只在开发中出现过的中间版本写逐步迁移。开发库在中间版本之间由开发者手动处理。

每次改动 `schema.sql` 都递增版本号，让结构不同的旧开发库被明确拒绝，而不是被当成当前结构误读。迁移只写一个：从上一发布版的数据库版本直接到当前版本，结构再变时修改这一个迁移，并保留对应回归（用上一发布版标签中的 `schema.sql` 副本建库、写入代表性数据，升级后数据完整可用；副本随测试保存）。迁移在打开数据库时于事务内执行，失败则保持原库不变并报告错误。除上一发布版和当前版本外，其他版本仍按上文拒绝。

| 发布版 | 数据库版本 |
| ---- | ---- |
| v0.1.0 | 14 |
| v0.2.0 | 14 |

发版时在表中补一行。

## 配对状态与目标恢复

控制设备记录包含 `device_type` 和 Unix 秒的 `last_seen_at`。`endpoints.device_checked_at` 保存最近一次设备同步请求的开始时间，按租户和 IN/OUT 节流 30 秒，重开数据库后仍有效。快照不发起同步；网页或桌面显式请求协调器核对上游列表。读取失败保留记录，零设备才清除；多设备保留记录，在 `input_pairings.error` 保存 `in_multiple_devices`，不撤权且不改变 pending，下一次配对开始时清除该提示。

`input_devices` 按租户 + IN 保存唯一控制设备的 client ID、名称、平台和型号；快照只读本地。`input_pairings` 保存 pending、配对有效期及异步错误码，不保存配对码。开始撤权前先写 pending；清理失败保留原设备记录，但 pending 期间快照不显示为当前设备。确认清空后删除旧记录，发码后恰好出现一台设备时，在事务内保存新记录并清除 pending；有效期内出现多台则撤销全部设备，保留冲突错误及 pending，确认清空后移除设备记录。停止/删除/再次配对会取消并等待跟踪，停止保留已完成的配对。进程意外中断后只恢复仍在有效期内的跟踪，pending 跨重启保留；删除 IN 时外键一并清理两张表。

`target_records` 按租户 + OUT 保存当前目标的名称、online、Unix 秒 last_seen_at 和配对提示；仅匹配当前目标的记录进入快照。配对、显式电脑同步及运行中的探测共用这份记录。目标缺失保留上次元数据并记录 `out_target_missing`，额外电脑记录 `out_multiple_environments`；不撤权，提示保留至重新配对成功。读取失败不覆盖记录；未授权或重新配对中不请求上游。OUT 与 IN 共用持久同步节流，运行中探测保持原有周期，不受显式同步节流限制。重新配对成功在同一事务内替换目标及全部电脑元数据、清除提示和未完成记录，并重置同步节流。

`output_pairings` 保存（租户 + OUT）未完成记录，不保存配对码。原目标和名称在重新配对期间保留；开始远端撤权前先保存未完成记录。链路协调器等待旧任务退出后才执行配对，绑定及原启用设置保留。未完成记录存在时，显式启动和进程恢复均不能连接旧目标；重新配对成功后，在同一事务里保存唯一目标、名称和版本并删除未完成记录，然后按原启用设置恢复链路。

撤权未完成、应答丢失、配对后的环境数量不是一个，或最终保存失败，均保留该记录与原目标；重试时重新读取此 OUT 的全部可访问环境并先清空，再使用新提交的配对码配对。旧环境的撤权结果以此 OUT 的环境列表确认，不把单独的 404 当作完成。删除 OUT 仍通过原注册撤权，完成本地删除时一并清理未完成记录。

离线备份需包含该表、绑定、启用设置、目标与原密钥；恢复未完成记录不会自动重用旧配对码或继续配对。此状态不改变设备 ID、公钥或 OUT 注册。设备名称只作展示，不能用于身份或路由。

## 部署时的备份与恢复顺序

用户可执行的备份恢复步骤见[服务器部署指南](../guide/server.zh.md#停止升级和备份)和[桌面版指南](../guide/desktop.zh.md#数据和备份)。下面是实现层面的顺序要求。

1. 正常停止服务器及全部管理 CLI，确认退出并保持维护期间独占数据库。Compose 的停止方式见 [部署说明](AUTHORIZATION.md#docker-compose-部署)。不要同时运行源实例与恢复实例。
2. 异常退出时先保留完整状态目录和相关日志文件，在独占条件下完成 SQLite 恢复并正常关闭；不能删掉热日志后仅复制主数据库。清洁关闭后的当前 `DELETE` 模式可复制主数据库文件。
3. 将数据库与**原主密钥文件**分别备份到私有位置，记录相同的备份批次与程序版本。密钥目录不在数据库目录内部，密钥文件保持服务用户属主及 `0600` 权限；备份程序也不能打印密钥。数据库与密钥缺一不可。
4. 恢复到未被使用的新目录或新卷，恢复属主和权限，配置 `BRIDGE_DATABASE`、`BRIDGE_MASTER_KEY` 及原部署入口；使用兼容 schema 的程序。恢复不执行 `init`，不生成新密钥，也不覆盖仍运行的实例。
5. 上线前核对账号授权、设备身份、绑定与待完成操作。旧快照可能含过期 refresh token、已撤销的注册或仍有效的管理会话；根据实际状态重新授权、完成待清理操作，必要时用管理密码重置使旧会话失效。数据库能打开不等于上游远控已恢复。

当前提供测试和人工操作顺序，没有实现在线备份、自动备份调度、异地备份加密或自动灾备切换。
